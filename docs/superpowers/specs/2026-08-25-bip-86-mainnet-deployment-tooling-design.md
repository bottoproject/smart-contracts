# BIP-86 Mainnet Deployment Tooling Design

## Purpose

Provide a reproducible, reviewable Node 24 workflow for preparing and
verifying the `BottoLiquidityMiningV2` to `BottoLiquidityMiningV3` mainnet
upgrade. The tooling separates deployment of the V3 implementation from the
privileged transactions that activate V3 and recover expired BOTTO rewards.

The scripts must never submit the ProxyAdmin upgrade or reward-recovery
transactions. They produce calldata for an operator to inspect and execute
through the owner account or a Safe.

## Deployment Baseline

All commands target Ethereum mainnet and the fixed BIP-86 deployment:

- Chain ID: `1`
- Liquidity-mining proxy: `0xf8515Cae6915838543bCD7756F39268CE8F853Fd`
- Expected V2 implementation: `0x49129912b35283DC64476641837DFE856B48Fa81`
- Expected ProxyAdmin: si,`0x61b4A813Fd4e361d40339bcA4d8d4E83Be78038D`
- Expected contract and ProxyAdmin owner:
  `0xcC23e5a344EB4E99114a8F25f6037951A39AA858`
- BOTTO token: `0x9dfad1b7102d46b1b197b90095b5c4e9f5845bba`
- DAO treasury: `0x35bb964878d7B6ddFA69cF0b97EE63fa3C9d9b49`
- Claim deadline: `1774915199` (March 30, 2026 23:59:59 UTC)

The scripts reject any mismatch instead of accepting command-line overrides
for these governance-controlled addresses.

## Toolchain Boundary

Truffle remains the authoritative compiler and historical contract-test
runner. Hardhat is added only as the supported deployment and mainnet-fork
runtime. Both use Solidity `0.7.6` and optimizer settings of 200 runs. Hardhat
compiles a generated, untracked mirror of `contracts/` to produce the
validation metadata required by the OpenZeppelin plugin. The Hardhat and
Truffle executable bytecode must match after removing only the Solidity CBOR
metadata suffix. The deployment factory uses the complete Truffle artifact,
whose creation and deployed hashes must match the reproducible manifest
generated by `npm run build:reproducible`. Any mismatch aborts the command, so
Hardhat cannot silently become a second authoritative V3 build.

The deployment tooling uses a current, pinned Hardhat release and
`@openzeppelin/hardhat-upgrades`. It must run under the repository's pinned
Node `24.10.0` and npm `11.6.1` versions.

## Commands and Responsibilities

### `npm run deploy:inspect`

Reads mainnet state and checks:

- network chain ID;
- code exists at the proxy, implementation, and ProxyAdmin addresses;
- the EIP-1967 implementation and admin slots match the baseline;
- `owner()` through the proxy and on the ProxyAdmin match the expected owner;
- the reproducible manifest and Hardhat V3 bytecode agree.

It performs no transaction and requires only `MAINNET_RPC_URL`.

### `npm run deploy:prepare`

Runs the inspection checks, imports the existing transparent proxy and V2
implementation into the local OpenZeppelin manifest, validates V2-to-V3
storage compatibility, and deploys the V3 implementation. It does not update
the proxy.

This is the only command that can broadcast a transaction. It requires
`MAINNET_RPC_URL`, `DEPLOYER_PRIVATE_KEY`, and the explicit acknowledgement
`BOTTO_DEPLOYMENT_MODE=prepare-mainnet-v3`. The deployer need not own either
the proxy or the implementation contract. The command refuses a chain other
than chain ID 1.

On success it writes an untracked JSON record under
`deployments/runtime/mainnet-v3-preparation.json` containing:

- chain ID and block number;
- proxy, old implementation, new implementation, ProxyAdmin, and owners;
- V3 deployed-bytecode hash;
- reproducible artifact hash;
- transaction hash for the implementation deployment;
- generated ProxyAdmin upgrade calldata.

The runtime directory is ignored by Git because transaction-specific output
is not a reproducible source artifact.

### `npm run deploy:propose`

Reads the preparation record, re-runs inspection, verifies that the recorded
V3 bytecode exists and matches the reproducible artifact, and prints a
machine-readable transaction proposal:

- target: the fixed ProxyAdmin;
- value: zero;
- calldata: `upgrade(proxy, newImplementation)`;
- expected sender: the fixed ProxyAdmin owner.

It never requests a signer and never sends a transaction.

### `npm run deploy:verify`

Reads the preparation record and verifies the live proxy's EIP-1967
implementation is the recorded V3 implementation. It also checks the proxy
admin and both owners, and reads `CLAIM_DEADLINE()` and `DAO_TREASURY()`
through the proxy. It performs no transaction.

### `npm run deploy:recover-proposal`

Requires a successful post-upgrade verification, confirms the latest block is
after the claim deadline, reads the proxy's BOTTO balance, and prints a
machine-readable transaction proposal:

- target: the liquidity-mining proxy;
- value: zero;
- calldata: `recoverUnclaimedRewards()`;
- expected sender: the fixed contract owner;
- expected recipient and current BOTTO amount.

It never requests a signer and never sends a transaction. The balance is
informational and may change before execution; the contract deliberately
recovers its full BOTTO balance at execution time.

## Shared Safety Module

A focused deployment module owns all fixed addresses, ABI fragments, EIP-1967
reads, bytecode hashing, chain checks, JSON proposal construction, and runtime
record validation. Each command delegates to this module so safety checks
cannot drift between scripts.

The module distinguishes three states:

1. `v2`: the proxy points to the approved V2 implementation;
2. `prepared`: V3 is deployed but the proxy still points to V2;
3. `upgraded`: the proxy points to the V3 address in the preparation record.

Any other implementation is an unknown state and aborts every command.

## Mainnet-Fork Test

The integration test starts from a pinned post-deadline mainnet block supplied
by the test configuration. It derives a staker with a non-zero position from
the proxy's `Stake` event history at that block, then impersonates that staker
and the known ProxyAdmin and contract owner only inside Hardhat Network. It
exercises the exact operational sequence:

1. confirm the fork starts on the expected V2 implementation;
2. import V2 and validate/prepare V3;
3. execute the generated ProxyAdmin upgrade calldata;
4. verify V3 constants and preserved representative proxy state;
5. execute the generated recovery calldata;
6. verify all proxy BOTTO is transferred to the fixed treasury;
7. verify a staker can still withdraw their complete LP principal afterward.

The fork test skips with an explicit message when `MAINNET_RPC_URL` is absent;
CI can opt into it by providing the URL. Unit tests cover all pure validation
and proposal-generation logic without network access.

## Error Handling

Every command exits non-zero on a failed invariant and prints the observed and
expected values. Private keys, full RPC URLs, and provider credentials must
never be logged or written to runtime records. A malformed or incomplete
preparation record is rejected before any network action.

The preparation command must fail before requesting a signer if its explicit
mainnet acknowledgement is absent. It must also fail if the proxy no longer
points to the approved V2 implementation, preventing a repeated or stale
preparation run from silently targeting a changed deployment.

## Documentation

The repository README will describe the operator sequence, required
environment variables, which commands are read-only, and the two human-signed
transactions. It will state that `truffle migrate --network mainnet` is not a
supported BIP-86 deployment path and that `recoverUnclaimedRewards()` is a
separate irreversible action after the upgrade.

## Non-Goals

- Storing or managing production private keys.
- Automatically submitting the ProxyAdmin upgrade.
- Automatically submitting reward recovery.
- Moving ProxyAdmin or contract ownership.
- Replacing the historical Truffle tests or reproducible compiler pipeline.
- Verifying source code through an explorer API; the preparation record and
  reproducible artifact provide the inputs for a separately reviewed explorer
  verification step.
